# Документ требований багфикса

## Introduction

Пользователь сообщает о наборе связанных дефектов, которые накопились в приложении San-Mes (Expo / React Native, соцсеть-мессенджер, приоритет iOS) и **не были устранены предыдущими итерациями «оптимизации»**. Симптомы:

- приложение деградирует **со временем работы** — чем дольше сессия, тем сильнее лаги;
- сильные тормоза на **слабых устройствах**;
- лаги при включённом **Low Power Mode** / низком заряде батареи;
- **дёргается интерфейс** при скролле, вьюпорт «нуджится» (самопроизвольно подпрыгивает);
- **контент исчезает, а затем появляется неправильный** (чужая картинка/размер/состояние в ячейке списка);
- **кэширование данных не «как в Telegram»** — контент мигает и проходит цикл «пусто → неправильно → правильно» вместо мгновенной отрисовки из кэша;
- **невозможно опубликовать изображение** — `upload failed (401)` / `unauthorised`;
- **не открывается админ-панель**.

### Центральный дефект: результат нельзя измерить

Главная причина фрустрации — не отдельные лаги, а то, что **ни один предыдущий раунд правок нельзя было ни подтвердить, ни опровергнуть**. Правки формулировались как «стало плавнее», без числового «до» и «после», без фиксированного эталонного устройства и без release-сборки. Поэтому этот документ трактует **отсутствие измеримости как дефект первого класса** (Блок A) и требует, чтобы каждое остальное требование имело числовой критерий приёмки. Требование «стало плавнее» в этом документе не является приёмочным критерием ни для одного пункта.

### Что уже было запланировано ранее и почему симптомы остались

В репозитории уже есть спеки, частично покрывающие эту область. Настоящий документ **их не дублирует** — он фиксирует остаточные симптомы и явно отмечает, что именно из ранее запланированного не дало результата:

| Спека | Что покрывала | Остаточный симптом |
|---|---|---|
| `.kiro/specs/music-and-performance-fixes` | лаги табов, тяжёлый чат, вкладки профиля, зависания контекстных меню | лаги остались, но пользователь описывает их теперь **как функцию времени сессии, класса устройства и режима питания** — то есть по осям, которых в той спеке не было |
| `.kiro/specs/offline-first-cache` | cache-first + stale-while-revalidate, отказоустойчивость SQLite | цикл «пусто → неправильно → правильно» всё ещё виден пользователю |
| `.kiro/specs/per-account-cache` | Telegram-подобный кэш, изоляция по аккаунтам, отсутствие `Visible_Reload` | мигание и перерисовка сохраняются на части экранов |
| `.kiro/specs/async-storage-offline` | офлайн-хранилище | — |
| `.kiro/specs/cloudflare-d1-migration` | перенос данных на D1 | админ-панель, которая читает метрики D1 через Worker, недоступна |
| `.kiro/specs/app-polish-perf-security` | **папка пуста — спека не была написана** | вся тема perf/security осталась незафиксированной |

Общая причина, по которой предыдущие раунды не сработали: правки применялись **точечно и вслепую**, без инструмента, который показал бы, помогли они или нет. Инструмент в приложении при этом уже есть (`src/services/perfMonitor.ts` — два независимых потока FPS, длинные задачи, ранжирование маршрутов по «janky»), но у него нет ни зафиксированных бюджетов, ни протокола прогона, ни сравнения «до/после».

### Установленные факты (проверены чтением кода)

Проверено в текущем состоянии рабочей копии:

1. **`babel.config.js` содержит только `react-native-reanimated/plugin`.** `babel-plugin-transform-remove-console` отсутствует, то есть все вызовы `console.*` остаются в release-бандле. В `src/` + `app/` найдено 26 таких мест.
2. **`expo-battery@~10.0.8` присутствует в `package.json`, но не импортируется ни в `src/`, ни в `app/`.** Признак Low Power Mode нигде не читается — сценарий энергосбережения в приложении не обрабатывается вообще.
3. **`isWeakDevice()` (`src/utils/deviceCapability.ts`) вычисляется один раз за сессию и используется только в `useAmbientAnimationGate`** (ambient-частицы сезонных тем). Он не влияет на ленту, чат, glass, blur или `drawDistance`.
4. **`useRecyclingState` (FlashList v2) не используется нигде.** При этом внутри перерабатываемых ячеек ленты живёт локальный `useState`: в `PostCard` — `primed` и `heroAspect`, в `ImageCarousel` — `activeIndex` и `firstAspect`. Только для `heroAspect` в коде есть сброс, привязанный к URI hero-изображения.
5. **У `AnimatedFlashList` в `app/(tabs)/index.tsx` не задан `getItemType`**, хотя карточки визуально разнотипны (только текст / одно изображение / карусель). Заданы `drawDistance={250}`; `maintainVisibleContentPosition` в v2 включён по умолчанию.
6. **В репозитории уже зафиксирован прецедент регрессии рециклинга:** комментарий в `src/__tests__/integration/performanceStructural.integration.test.tsx` объясняет, что `(tabs)/messages.tsx` осознанно оставлен на `FlatList`, потому что FlashList там давал «rows missing until a tab switch».
7. **Цепочка 401 при загрузке изображения полностью прослежена.** `api/r2-upload.ts` вызывает `verifyWorkerToken(extractBearer(...))` и при `null` отвечает `401 {error:'unauthorised'}`. `api/_lib/verifyToken.ts` работает **fail-closed**: `if (!secret || !token) return null`, где `secret = process.env.JWT_SECRET`. Дополнительно проверяются `header.alg === 'HS256'`, `payload.iss === 'san-mes-api'`, `exp`/`nbf` и наличие `sub`. Клиент `src/lib/r2.ts` отправляет `Authorization: Bearer ${getAuthToken()}` корректно, а при отсутствии токена возвращает собственную ошибку `'not signed in'` — значит 401 приходит именно с сервера. **Первичная гипотеза: `JWT_SECRET` на Vercel не задан или расходится с секретом Worker'а** (`workers/api/src/auth.ts`, `wrangler secret put JWT_SECRET`). Вторичные: истёкший токен, рассинхрон issuer.
8. **Админ-панель — тот же класс ошибки.** `api/admin/status.ts`: `const ADMIN_PASSWORD = process.env.ADMIN_KEY || ''` без literal-фоллбэка → без переменной эндпоинт отдаёт `503 {error:'admin_not_configured'}`, при несовпадении `x-admin-key` → `401 {error:'Unauthorized'}`. Отдельно `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` могут быть не заданы → `r2_not_configured`, и метрики хранилища деградируют в оценку по числу постов с изображениями. В комментариях того же файла зафиксировано, что ранее закоммиченные креды (админ-пароль и R2 S3 keypair) **остаются в git-истории, должны считаться скомпрометированными и подлежат ротации**.
9. `app.json`: `version: "1.2.0"`, `runtimeVersion.policy: "appVersion"`. Объявлены `NSPhotoLibraryUsageDescription`, `NSPhotoLibraryAddUsageDescription`, `NSCameraUsageDescription`, `UIBackgroundModes: ["audio"]`.

Пункт 4 — наиболее вероятное объяснение симптома «контент исчез, потом появился неправильный»: FlashList при выходе ячейки из вьюпорта **не размонтирует** компонент, а перерисовывает его с другим `item`, поэтому `useState` внутри ячейки «протекает» между разными постами. Пункт 6 показывает, что этот класс регрессии в проекте уже наблюдался.

### Протокол измерения (обязателен для всех числовых критериев)

- **Только release-сборка.** В dev-режиме производительность нерепрезентативна (прямо указано в RN Performance Overview): dev-бандл несёт валидацию пропсов, LogBox и незаминифицированный код. Любой замер в Expo Go / dev-клиенте не является доказательством.
- **Два независимых FPS.** JS-поток и UI/main-поток измеряются и отчитываются раздельно — просадка только JS-потока и просадка только UI-потока имеют разные причины и разные исправления.
- **Эталонные устройства.** `Weak` — устройство, которое текущий `isWeakDevice()` классифицирует как слабое (iOS year class ≤ 2020, т.е. iPhone 11 / SE 2 и старше; либо Android с API ≤ 30 или < 3 ГБ RAM). `Mid` — iPhone 12/13 класса. Каждый числовой бюджет фиксируется отдельно для `Weak` и `Mid`.
- **Фиксированные сценарии.** Каждый замер выполняется по записанному сценарию с фиксированным объёмом данных (число постов в ленте, число сообщений в чате), чтобы «до» и «после» были сопоставимы.
- **Термостабилизация.** Замеры не начинаются, пока устройство не остыло до нормальной температуры и не отключено от зарядки — иначе троттлинг делает результат невоспроизводимым.

### Ограничения соответствия (Apple Developer Program License Agreement)

Действуют как жёсткие ограничения на все требования ниже (см. `.kiro/steering/apple-compliance.md`):

- **Никаких новых нативных permission'ов через OTA.** `eas update` доставляет только JS и ассеты. Всё, что требует нативного модуля или новой строки `NS*UsageDescription`, идёт только новой нативной сборкой. `runtimeVersion.policy` = `appVersion`, поэтому OTA доедет только до сборок с той же версией приложения.
- **`expo-sensors` и motion-permissions не возвращать** (сборка 82 уже получила нежелательный prompt «Motion & Fitness», риск по guideline 5.1.1).
- **Никаких IDFA и трекинг-SDK.** Если для измерения производительности предлагается Sentry или любая другая удалённая телеметрия — это трактуется как сбор данных о пользователе: нужен явный consent до первой отправки, обновление privacy policy и App Store privacy questionnaire, отсутствие fingerprinting и только opaque per-install идентификаторы. Локальный `perfMonitor`, который не отправляет данные с устройства, таких обязательств не создаёт и поэтому является предпочтительным инструментом.
- **ATS остаётся HTTPS-only.** `NSAllowsArbitraryLoads: true` не вводится. Все эндпоинты (Worker, Vercel, R2, музыкальные провайдеры) — HTTPS.
- **Флоу жалобы на контент и блокировки пользователей не ломать** (App Review guideline 1.2).
- **Риск по SoundCloud не усугублять** — не добавлять новых прямых stream-вызовов.

### Границы

Этот багфикс **не** является редизайном, не меняет продуктовое поведение экранов, не переписывает слой кэша с нуля (спеки `offline-first-cache` и `per-account-cache` остаются в силе как база) и не вводит новых нативных зависимостей без отдельного подтверждения.

## Bug Analysis

### Current Behavior (Defect)

Текущее (дефектное) поведение.

**Блок A — Отсутствие измеримости**

1.1 WHEN команда применяет изменение производительности THEN the system не даёт зафиксированного числового «до/после»: бюджеты JS fps, UI fps, TTI, времени до первого контента из кэша, числа blank-кадров и потребления памяти нигде не заданы, поэтому результат правки невозможно ни подтвердить, ни опровергнуть.

1.2 WHEN производительность проверяется THEN the system измеряется в dev-режиме, где показатели нерепрезентативны, и результат переносится на release-поведение без обоснования.

1.3 WHEN просадка производительности случается у пользователя THEN the system не даёт воспроизводимого сценария и не привязывает просадку к маршруту, классу устройства и режиму питания, хотя `src/services/perfMonitor.ts` уже собирает JS/UI fps, длинные задачи и per-route hotspots — у собранных данных нет ни порогов, ни протокола сравнения.

**Блок B — Деградация при длительной сессии**

1.4 WHEN пользователь работает в приложении продолжительное время (десятки минут, множество переходов между лентой, чатами и профилями) THEN the system прогрессивно замедляется: лаги усиливаются по мере роста времени сессии, тогда как сразу после запуска те же экраны работают быстрее.

1.5 WHEN пользователь многократно входит и выходит с экранов THEN the system накапливает подписки, таймеры и слушатели, не возвращаясь к базовому количеству после ухода с экрана, из-за чего фоновая работа на каждый кадр растёт со временем.

1.6 WHEN пользователь долго скроллит ленту с подгрузкой страниц THEN the system наращивает объём данных в памяти и размер кэша без наблюдаемого потолка, что увеличивает стоимость каждой перерисовки и повышает риск jetsam-kill на слабом устройстве.

1.7 WHEN сессия длится долго THEN the system не даёт способа отличить деградацию от роста числа объектов в памяти, от накопления слушателей и от роста нативной памяти изображений — все три причины проявляются одинаково и потому исправляются наугад.

**Блок C — Слабые устройства**

1.8 WHEN приложение запущено на устройстве, которое `isWeakDevice()` классифицирует как слабое THEN the system выполняет тот же объём работы на кадр, что и на флагмане: единственный потребитель этого признака — `useAmbientAnimationGate` (ambient-частицы сезонных тем), поэтому ни лента, ни чат, ни glass/blur-поверхности, ни `drawDistance` на слабом устройстве не облегчаются.

1.9 WHEN пользователь скроллит ленту или открывает тяжёлый чат на слабом устройстве THEN the system даёт сильные тормоза, при которых интерфейс перестаёт откликаться на касания в течение заметного времени.

1.10 WHEN на слабом устройстве применяется правка производительности THEN the system не проверяется на этом классе устройств отдельно от быстрого, поэтому регрессии, видимые только на слабом железе, проходят незамеченными.

**Блок D — Режим энергосбережения и низкий заряд**

1.11 WHEN на iOS включён Low Power Mode THEN the system не знает об этом: `expo-battery` есть в `package.json`, но не импортируется ни в `src/`, ни в `app/`, и ни одна анимация, ни один интервал и ни один параметр рендеринга не адаптируются к режиму энергосбережения.

1.12 WHEN Low Power Mode активен THEN the system продолжает выполнять тот же объём работы на кадр, хотя ОС ограничивает CPU/GPU и снижает частоту обновления (до 30 Гц), из-за чего анимации, считающиеся на JS-потоке, деградируют катастрофически, а не пропорционально.

1.13 WHEN заряд батареи низкий или устройство троттлится из-за нагрева THEN the system не снижает фоновую активность (периодические таймеры, поллинг, префетч, ambient-анимации) и тем усугубляет и лаги, и расход заряда.

**Блок E — Дёргание интерфейса и «нудж» вьюпорта**

1.14 WHEN пользователь скроллит ленту THEN the system дёргается: кадры пропускаются неравномерно, и скролл ощущается рывками, а не непрерывным.

1.15 WHEN изображение в карточке выше вьюпорта завершает декодирование и карточка меняет свой размер THEN the system сдвигает вьюпорт («нудж»), из-за чего читаемая позиция уезжает под пальцем.

1.16 WHEN пользователь нажимает на элемент, запускающий тяжёлое действие THEN the system выполняет эту работу в том же кадре, что и обработку нажатия, из-за чего отклик на касание задерживается на длину задачи.

**Блок F — Рециклинг списков: контент исчезает и подменяется**

1.17 WHEN ячейка ленты выходит из вьюпорта и переиспользуется под другой пост THEN the system сохраняет локальное состояние предыдущего элемента: `useRecyclingState` не используется нигде, а внутри перерабатываемых ячеек живёт `useState` (`primed` и `heroAspect` в `PostCard`, `activeIndex` и `firstAspect` в `ImageCarousel`), поэтому новый пост отрисовывается с состоянием старого.

1.18 WHEN пользователь быстро скроллит ленту THEN the system показывает **сначала пустое место, затем неправильный контент** (изображение или пропорции предыдущего поста), и только после этого — правильный: ровно тот наблюдаемый цикл, который описывает пользователь.

1.19 WHEN в ленте соседствуют визуально разнотипные карточки (только текст / одно изображение / карусель) THEN the system переиспользует ячейки между несовместимыми типами, потому что `getItemType` у `AnimatedFlashList` в `app/(tabs)/index.tsx` не задан.

1.20 WHEN список настроен с `removeClippedSubviews` THEN the system на iOS может **терять уже отрисованный контент** (документированный побочный эффект этого флага), и в проекте это уже наблюдалось: `(tabs)/messages.tsx` осознанно оставлен на `FlatList`, потому что FlashList там давал «rows missing until a tab switch».

**Блок G — Кэш ведёт себя не как в Telegram**

1.21 WHEN пользователь открывает экран, для которого кэш уже есть THEN the system показывает видимый цикл «пусто → неправильно → правильно» (пустое состояние или спиннер, затем устаревшие/чужие данные, затем актуальные) вместо мгновенной отрисовки кэша.

1.22 WHEN пользователь возвращается на уже посещённый экран (переключение таба, выход и повторный вход в профиль или чат) THEN the system мигает и перерисовывается, вместо того чтобы отрисовать кэш сразу и обновить его молча в фоне.

1.23 WHEN фоновое обновление приносит данные, идентичные кэшированным THEN the system всё равно вызывает перерисовку, тратя работу на кадр без изменения того, что видит пользователь.

**Блок H — Невозможно опубликовать изображение (401)**

1.24 WHEN пользователь публикует пост, комментарий, сообщение или обновляет аватар/баннер с изображением THEN the system завершает загрузку ошибкой `upload failed (401)` с телом `{"error":"unauthorised"}`, и изображение не публикуется.

1.25 WHEN `api/r2-upload.ts` обрабатывает запрос THEN the system отвергает **любой** предъявленный токен, если `process.env.JWT_SECRET` на Vercel не задан или не совпадает с секретом Worker'а: `verifyWorkerToken` реализован fail-closed (`if (!secret || !token) return null`), поэтому неверная конфигурация окружения внешне неотличима от неверного токена.

1.26 WHEN загрузка падает с 401 THEN the system показывает пользователю сырую строку `upload failed (401) …` и не даёт ни ему, ни разработчику способа отличить «на сервере не настроен секрет» от «токен истёк» и от «пользователь не авторизован»; при этом черновик поста и выбранное изображение теряются.

**Блок I — Админ-панель недоступна и конфигурация недиагностируема**

1.27 WHEN администратор открывает `app/settings/admin.tsx` THEN the system не открывает панель: `api/admin/status.ts` отдаёт `503 {"error":"admin_not_configured"}` при незаданном `ADMIN_KEY` (literal-фоллбэк удалён намеренно) либо `401 {"error":"Unauthorized"}` при несовпадении `x-admin-key`.

1.28 WHEN панель не открывается THEN the system не позволяет из UI отличить «переменная окружения не задана» (503) от «неверный пароль» (401) и от «сервис недоступен», из-за чего проблема воспринимается как «что-то с хостингом/сервером» и не диагностируется.

1.29 WHEN `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` не заданы THEN the system молча деградирует метрики хранилища до оценки `postsWithImg × 180 КБ` с флагом `measured: false`, и панель показывает вычисленное значение без явного признака, что измерение не проводилось. Дополнительно: ранее закоммиченные админ-пароль и R2 S3 keypair остаются в git-истории и до сих пор не подтверждены как ротированные.

### Expected Behavior (Correct)

Корректное поведение. Нумерация соответствует дефектам выше: `2.N` исправляет `1.N`.

**Блок A — Измеримость**

2.1 WHEN команда применяет изменение производительности THEN the system SHALL иметь зафиксированный набор числовых бюджетов, и каждое изменение SHALL сопровождаться замером «до» и «после» по одному и тому же сценарию. Бюджеты (базовая версия, уточняется первым же замером на реальных эталонных устройствах):

| Метрика | `Mid` | `Weak` |
|---|---|---|
| JS fps, средний при скролле ленты | ≥ 55 | ≥ 45 |
| JS fps, минимум в окне 5 с | ≥ 45 | ≥ 30 |
| UI fps, средний при скролле | ≥ 58 | ≥ 50 |
| Длинные задачи JS-потока | ни одной > 250 мс | ни одной > 400 мс |
| TTI (холодный старт → лента интерактивна) | ≤ 2.5 с | ≤ 4.0 с |
| Время до первого контента из кэша | ≤ 300 мс | ≤ 500 мс |
| Кадров с пустой/неправильной ячейкой при скролле | 0 | 0 |
| Рост памяти за 30 мин сценария | ≤ 15 % от значения на 5-й минуте | ≤ 15 % |

2.2 WHEN производительность проверяется THEN the system SHALL измеряться **только в release-сборке** на физическом устройстве; замер в dev-режиме, Expo Go или dev-клиенте SHALL NOT считаться доказательством улучшения или регрессии.

2.3 WHEN просадка производительности случается THEN the system SHALL привязывать её к маршруту, классу устройства (`Weak`/`Mid`) и режиму питания (Low Power Mode вкл/выкл), и `src/services/perfMonitor.ts` SHALL получить явные пороги, соответствующие таблице 2.1, чтобы уже собираемые им JS/UI fps, длинные задачи и per-route hotspots давали вердикт «в бюджете / вне бюджета», а не только числа. Данные SHALL оставаться локальными на устройстве; любая удалённая отправка SHALL требовать explicit consent, обновления privacy policy и App Store privacy questionnaire.

**Блок B — Длительная сессия**

2.4 WHEN пользователь работает в приложении 30 минут по фиксированному сценарию THEN the system SHALL удерживать метрики из таблицы 2.1 в тех же границах, что и на 5-й минуте, с допуском не более 10 % по fps и не более 15 % по памяти.

2.5 WHEN пользователь уходит с экрана THEN the system SHALL возвращать число активных подписок, таймеров и слушателей к базовому значению: после цикла «10 раз войти и выйти» счётчик SHALL совпадать со значением после первого входа.

2.6 WHEN пользователь долго скроллит ленту с подгрузкой страниц THEN the system SHALL удерживать объём данных в памяти и размер кэша под явным потолком с вытеснением старых элементов, и потолок SHALL быть задан числом, а не подразумеваться.

2.7 WHEN сессия длится долго THEN the system SHALL позволять отличить три причины деградации друг от друга — рост числа объектов в памяти, накопление слушателей/таймеров и рост нативной памяти изображений — по отдельным наблюдаемым счётчикам, чтобы исправление адресовало установленную причину, а не предполагаемую.

**Блок C — Слабые устройства**

2.8 WHEN приложение запущено на устройстве класса `Weak` THEN the system SHALL сокращать объём работы на кадр на тяжёлых экранах (лента, чат, профиль), а не только гасить ambient-частицы: признак слабого устройства SHALL влиять как минимум на объём предварительного рендеринга списков, на число одновременно декодируемых изображений и на сложность декоративных поверхностей (glass/blur/градиенты).

2.9 WHEN пользователь скроллит ленту или открывает тяжёлый чат на устройстве класса `Weak` THEN the system SHALL укладываться в колонку `Weak` таблицы 2.1 и SHALL сохранять отклик на касание: задержка между касанием и визуальной реакцией SHALL NOT превышать 150 мс.

2.10 WHEN применяется правка производительности THEN the system SHALL быть замерена на обоих классах устройств (`Weak` и `Mid`) раздельно, и улучшение на `Mid` при регрессии на `Weak` SHALL считаться неуспешным исправлением.

**Блок D — Режим энергосбережения**

2.11 WHEN на устройстве включён Low Power Mode THEN the system SHALL определять это состояние и реагировать на его изменение в течение сессии без перезапуска экрана. Реализация SHALL опираться на уже присутствующий в `package.json` `expo-battery` и SHALL NOT вводить новых нативных permission'ов; если нативный модуль отсутствует в текущем бинарнике, признак SHALL безопасно деградировать к «режим неизвестен → поведение как сейчас», а активация SHALL происходить только после новой нативной сборки, никогда через OTA.

2.12 WHEN Low Power Mode активен THEN the system SHALL деградировать плавно, а не катастрофически: SHALL удерживать fps на уровне не ниже 90 % от навязанного ОС потолка частоты обновления (то есть ≈ 27 fps при потолке 30 Гц), SHALL отключать или упрощать декоративные анимации и SHALL исключить анимации, которые считают кадры на JS-потоке, оставив только те, что исполняются нативно. Low Power Mode SHALL трактоваться как полноправный сценарий приёмки наравне с обычным режимом, а не как краевой случай.

2.13 WHEN заряд низкий, Low Power Mode включён или устройство троттлится THEN the system SHALL снижать фоновую активность — увеличивать интервалы периодических таймеров, ограничивать префетч и останавливать ambient-анимации — не нарушая доставку сообщений, уведомлений и работу офлайн-очереди.

**Блок E — Плавность скролла**

2.14 WHEN пользователь скроллит ленту THEN the system SHALL выдерживать равномерный ритм кадров в границах таблицы 2.1, без пропущенных кадров, воспринимаемых как рывок.

2.15 WHEN изображение выше вьюпорта завершает декодирование и меняет размер карточки THEN the system SHALL сохранять видимую позицию контента неизменной: вьюпорт SHALL NOT сдвигаться под пальцем пользователя.

2.16 WHEN пользователь нажимает на элемент, запускающий тяжёлое действие THEN the system SHALL отдавать визуальный отклик на касание в пределах 150 мс, выполняя тяжёлую работу после кадра отклика, а не в нём.

**Блок F — Рециклинг списков**

2.17 WHEN ячейка списка переиспользуется под другой элемент THEN the system SHALL сбрасывать всё локальное состояние ячейки к начальному значению для нового элемента **в том же кадре, в котором элемент подменяется** — до того, как ячейка будет отрисована. Состояние предыдущего элемента SHALL NOT быть видимым ни на одном кадре.

2.18 WHEN пользователь быстро скроллит ленту THEN the system SHALL NOT показывать цикл «пусто → неправильно → правильно»: каждая ячейка SHALL отрисовываться либо своим корректным контентом, либо нейтральным placeholder'ом того же размера, и SHALL NOT показывать контент другого элемента ни на один кадр.

2.19 WHEN в списке соседствуют визуально разнотипные элементы THEN the system SHALL предотвращать переиспользование ячеек между несовместимыми типами, объявив тип элемента для списка ленты.

2.20 WHEN список использует `removeClippedSubviews` THEN the system SHALL подтвердить на iOS в release-сборке, что уже отрисованный контент не пропадает; если пропадает — флаг SHALL быть снят на этом списке, а виртуализация обеспечена другими параметрами. Прецедент `(tabs)/messages.tsx` («rows missing until a tab switch») SHALL быть учтён: миграция этого списка на FlashList SHALL NOT выполняться в рамках этого багфикса без явного доказательства отсутствия регрессии.

**Блок G — Кэш «как в Telegram»**

2.21 WHEN пользователь открывает экран, для которого кэш уже есть THEN the system SHALL отрисовывать кэшированный контент синхронно, без спиннера и без пустого состояния, в пределах бюджета «время до первого контента из кэша» из таблицы 2.1, и SHALL обновлять его молча, когда придут свежие данные.

2.22 WHEN пользователь возвращается на уже посещённый экран THEN the system SHALL NOT показывать `Visible_Reload` (спиннер, пустой экран, мигание, очистку с последующим заполнением) при наличии кэша.

2.23 WHEN фоновое обновление приносит данные, идентичные кэшированным THEN the system SHALL NOT вызывать перерисовку: обновление SHALL применяться только при фактическом изменении данных.

**Блок H — Загрузка изображений**

2.24 WHEN авторизованный пользователь публикует пост, комментарий, сообщение или обновляет аватар/баннер с изображением THEN the system SHALL успешно загружать файл и возвращать публичный URL, а не `401 unauthorised`.

2.25 WHEN конфигурация серверной аутентификации проверяется THEN the system SHALL иметь `JWT_SECRET` на Vercel, **идентичный** секрету Cloudflare Worker (`wrangler secret put JWT_SECRET`, `workers/api/src/auth.ts`), и SHALL сохранять fail-closed-поведение `verifyWorkerToken` без изменений — исправляется конфигурация, а не проверка. Issuer `san-mes-api` и алгоритм `HS256` SHALL совпадать на обеих сторонах. Совпадение секретов SHALL быть проверяемо без раскрытия значения секрета (например, сравнением отпечатка, а не самого секрета).

2.26 WHEN загрузка не удаётся THEN the system SHALL различать причины и сообщать их по-разному: «сервер не настроен» (отсутствует `JWT_SECRET`), «сессия истекла — войдите заново» (истёкший или невалидный токен), «нет сети / таймаут». Пользователю SHALL показываться понятное сообщение и действие, а не сырая строка `upload failed (401) …`; черновик поста и выбранное изображение SHALL сохраняться, чтобы публикацию можно было повторить без повторного выбора файла. Диагностический ответ SHALL NOT раскрывать значений секретов и токенов.

**Блок I — Админ-панель**

2.27 WHEN администратор открывает `app/settings/admin.tsx` с корректным паролем THEN the system SHALL открывать панель и показывать статус сервисов и метрики; необходимые переменные окружения (`ADMIN_KEY` на Vercel и совпадающий admin-ключ в Worker) SHALL быть заданы.

2.28 WHEN панель не открывается THEN the system SHALL показывать в UI причину, различающую как минимум: «на сервере не настроен `ADMIN_KEY`» (503 `admin_not_configured`), «неверный пароль» (401 `Unauthorized`), «сервис недоступен / таймаут» (сетевая ошибка). Диагностическое сообщение SHALL NOT раскрывать значения ключей и SHALL NOT сообщать, какая именно переменная задана, кому-либо, кто не прошёл проверку пароля.

2.29 WHEN метрики хранилища не могут быть измерены THEN the system SHALL явно помечать значение как неизмеренное (`measured: false`) в самом UI, а не показывать оценку как факт. Дополнительно: ранее закоммиченные админ-пароль и R2 S3 keypair SHALL быть ротированы (новый keypair, новый пароль) до подачи в App Store — они остаются в git-истории и должны считаться скомпрометированными; ротация SHALL быть подтверждена явно, а не предположена.

### Unchanged Behavior (Regression Prevention)

Существующее поведение, которое ДОЛЖНО быть сохранено — для входов, не попадающих под условие бага.

**Функциональность**

3.1 WHEN пользователь просматривает ленту, чаты, профили и комментарии THEN the system SHALL CONTINUE TO отображать тот же контент и то же визуальное оформление, что и сейчас: этот багфикс не является редизайном.

3.2 WHEN пользователь отправляет сообщение, публикует пост или комментарий THEN the system SHALL CONTINUE TO работать через существующую офлайн-очередь (`offlineQueue`) с теми же гарантиями повторной отправки.

3.3 WHEN сеть недоступна THEN the system SHALL CONTINUE TO работать на кэшированных данных без сбоев, как это описано в `offline-first-cache` и `per-account-cache`.

3.4 WHEN пользователь переключает аккаунт THEN the system SHALL CONTINUE TO соблюдать изоляцию кэша по аккаунтам (`@acc:${accountId}:` namespace) и SHALL CONTINUE TO не стирать кэш при переключении.

3.5 WHEN приложение играет музыку в фоне THEN the system SHALL CONTINUE TO продолжать воспроизведение и показывать `MusicMiniBar`, включая режим энергосбережения: снижение фоновой активности по 2.13 SHALL NOT останавливать музыку.

3.6 WHEN приходит push-уведомление о новом DM, ответе на комментарий или новом подписчике THEN the system SHALL CONTINUE TO доставлять его: снижение фоновой активности SHALL NOT затрагивать доставку уведомлений.

3.7 WHEN уже работающие оптимизации активны THEN the system SHALL CONTINUE TO их применять: потолок нативной памяти изображений (`src/services/imageMemoryManager.ts`, ~96 МБ + сброс по низкой памяти), отложенная тяжёлая работа через `InteractionManager`, `maintainVisibleContentPosition`, нативный драйвер у существующих анимаций, кэш размеров изображений (`imageDimsCache`). Ни одна из них SHALL NOT быть отключена «для упрощения».

3.8 WHEN пользователь на устройстве класса `Mid` или новее и Low Power Mode выключен THEN the system SHALL CONTINUE TO показывать полное визуальное оформление: деградация по 2.8, 2.12 и 2.13 SHALL применяться только при выполнении соответствующего условия.

3.9 WHEN пользователь включил в системе Reduce Motion или Reduce Transparency THEN the system SHALL CONTINUE TO уважать эти настройки через существующие `useReducedMotion` и проверку в `LiquidGlass.tsx`, и новая логика режима питания SHALL NOT перекрывать их.

3.10 WHEN администратор пользуется остальными функциями админ-панели THEN the system SHALL CONTINUE TO выполнять их как сейчас; изменения касаются только доступности панели и диагностируемости конфигурации.

3.11 WHEN пользователь загружает изображение допустимого типа и размера THEN the system SHALL CONTINUE TO применять серверные проверки без ослабления: allowlist content-type, сверку magic bytes, лимит 4 МБ, allowlist префиксов бакета и таймаут загрузки 45 с на клиенте.

**Безопасность и соответствие**

3.12 WHEN эндпоинты Vercel обрабатывают запросы THEN the system SHALL CONTINUE TO работать fail-closed: отсутствие секрета SHALL CONTINUE TO означать отказ, а не пропуск. Literal-фоллбэки для `JWT_SECRET`, `ADMIN_KEY` и R2-кредов SHALL NOT быть возвращены, и никакие секреты SHALL NOT попадать в репозиторий.

3.13 WHEN исправления доставляются THEN the system SHALL CONTINUE TO соблюдать разделение каналов: JS/asset-изменения — через `eas update`, всё, что требует нативного модуля или новой строки `NS*UsageDescription` — только новой нативной сборкой. Ни один OTA-апдейт SHALL NOT вводить нового нативного permission'а.

3.14 WHEN состав permission'ов проверяется THEN the system SHALL CONTINUE TO объявлять ровно текущий набор: `NSPhotoLibraryUsageDescription`, `NSPhotoLibraryAddUsageDescription`, `NSCameraUsageDescription`, `UIBackgroundModes: ["audio"]`. `expo-sensors` и `NSMotionUsageDescription` SHALL NOT быть возвращены. IDFA, `NSUserTrackingUsageDescription` и трекинг-SDK SHALL NOT быть добавлены.

3.15 WHEN приложение выполняет сетевые запросы THEN the system SHALL CONTINUE TO использовать только HTTPS; `NSAllowsArbitraryLoads: true` SHALL NOT быть введён, а неиспользуемые entitlements SHALL NOT попадать в сборку.

3.16 WHEN собираются данные о производительности THEN the system SHALL CONTINUE TO не собирать пользовательские данные без явного consent и SHALL CONTINUE TO не выполнять fingerprinting: `isWeakDevice()` SHALL CONTINUE TO использовать только коарсные device-class-признаки, не объединяя их в стабильный идентификатор устройства, не сохраняя и не передавая их. Любая новая удалённая телеметрия SHALL требовать consent, обновления privacy policy и App Store privacy questionnaire до первой отправки.

3.17 WHEN пользователь жалуется на контент или блокирует другого пользователя THEN the system SHALL CONTINUE TO предоставлять эти флоу в рабочем состоянии (App Review guideline 1.2); ни один рефакторинг производительности SHALL NOT их удалить или сломать.

3.18 WHEN приложение воспроизводит музыку THEN the system SHALL CONTINUE TO использовать текущие источники без добавления новых прямых SoundCloud stream-вызовов; риск по §3.3.4.A.i SHALL NOT быть усугублён.

## Bug Conditions и Properties

Формализация условий ошибки. `F` — поведение до исправления, `F'` — после. `X` — вход (сценарий, устройство, режим питания, элемент списка, запрос).

### Общий вход измерения

```pascal
TYPE Measurement =
  { scenario:    ScenarioId        // фиксированный записанный сценарий
  , build:       "release" | "dev"
  , deviceClass: "Weak" | "Mid"
  , lowPower:    boolean
  , route:       string
  , elapsedMin:  number }          // минут с начала сессии
```

### Блок A — Измеримость

```pascal
FUNCTION isBugCondition_Measurability(X)
  INPUT: X of type PerfChange
  OUTPUT: boolean

  // Любое изменение производительности, у которого нет пары
  // сопоставимых замеров в release-сборке.
  RETURN X.isPerfChange
     AND (X.beforeMeasurement = null
          OR X.afterMeasurement = null
          OR X.beforeMeasurement.build <> "release"
          OR X.afterMeasurement.build <> "release"
          OR X.beforeMeasurement.scenario <> X.afterMeasurement.scenario)
END FUNCTION
```

```pascal
// Property: Fix Checking — каждое изменение доказуемо
FOR ALL X WHERE isBugCondition_Measurability(X) DO
  result <- F'(X)
  ASSERT result.beforeMeasurement <> null
     AND result.afterMeasurement <> null
     AND result.beforeMeasurement.build = "release"
     AND result.afterMeasurement.build = "release"
     AND result.beforeMeasurement.scenario = result.afterMeasurement.scenario
     AND result.verdict IN { "within_budget", "out_of_budget" }
     AND result.reportedPerDeviceClass = { "Weak", "Mid" }
END FOR
```

### Блок B — Деградация при длительной сессии

```pascal
FUNCTION isBugCondition_Degradation(X)
  INPUT: X of type Measurement
  OUTPUT: boolean

  RETURN X.build = "release" AND X.elapsedMin >= 30
END FUNCTION
```

```pascal
// Property: Fix Checking — метрики не деградируют со временем
FOR ALL X WHERE isBugCondition_Degradation(X) DO
  late  <- F'(X)                        // замер на 30-й минуте
  early <- F'(X WITH elapsedMin := 5)   // тот же сценарий, 5-я минута
  ASSERT late.jsFpsAvg  >= early.jsFpsAvg  * 0.90
     AND late.uiFpsAvg  >= early.uiFpsAvg  * 0.90
     AND late.memoryRss <= early.memoryRss * 1.15
     AND late.listenerCount = early.listenerCount   // ничего не накопилось
     AND late.timerCount    = early.timerCount
END FOR
```

```pascal
FUNCTION isBugCondition_Leak(X)
```
